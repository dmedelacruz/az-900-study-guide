## What Is Compute in the Cloud?

Every useful application ultimately needs a processor to run code — something that executes instructions, responds to requests, and produces results. In traditional IT, that processor lives in a physical server that your organization buys, racks, and maintains. In the cloud, that processing power is delivered as a service: you request it, use it, and pay for what you consume, without ever touching a physical machine.

Azure compute is the umbrella term for all the services that provide this processing capability. But "compute" is not a single product. Azure offers a whole spectrum of compute options, each optimized for different workload types, different management preferences, and different operational models. At one end of the spectrum, a **Virtual Machine** gives you complete control over an entire simulated server — you choose the OS, install the software, and manage every patch. At the other end, **Azure Functions** lets you run a small piece of code in response to an event without thinking about servers at all.

Between those extremes, you'll find app hosting platforms, container runtimes, orchestration engines, and desktop virtualization services — each trading off control for convenience in different ways.

Understanding the Azure compute portfolio is one of the most important skill sets for the AZ-900 exam. You'll be expected to distinguish between these services, recognize which type of workload each is best suited for, and understand the key characteristics that differentiate them. Let's walk through each service category.

## Virtual Machines

<KeyTerm term="Azure Virtual Machine (VM)">An on-demand, scalable compute resource that emulates a physical computer. Azure VMs are an Infrastructure as a Service (IaaS) offering — you choose the operating system, install software, and manage the OS patches and updates, while Azure manages the physical hardware underneath.</KeyTerm>

Think of a Virtual Machine as renting a fully functional computer that exists in Azure's data center. You get CPU, memory, disk, and network access — just like a physical server — but without owning the hardware. You connect to it over the network (via Remote Desktop for Windows or SSH for Linux), use it however you like, and stop paying when you're done.

Because VMs are IaaS, you are responsible for:

- **Operating system** — choosing Windows Server, Ubuntu, RHEL, or any supported OS
- **Patches and updates** — keeping the OS and installed software current
- **Installed software** — your runtime environments, applications, and agents
- **Security configuration** — firewalls, antivirus, access controls

Azure is responsible for:

- **Physical hardware** — the actual server blades, power, cooling, and physical network
- **Hypervisor** — the virtualization layer that runs multiple VMs on shared hardware
- **Physical security** — data center access controls

This division of responsibility makes VMs ideal when you need to **lift and shift** an existing on-premises workload to the cloud with minimal changes, or when your application requires a specific OS configuration, custom kernel settings, or legacy software that doesn't work on managed platforms.

<Callout type="tip">
A common AZ-900 exam question asks which compute service is IaaS. Virtual Machines are the primary IaaS compute option. Remember: IaaS = you manage the OS and above. App Service is PaaS (Azure manages the OS). Azure Functions is serverless (you only manage the code).
</Callout>

### VM Scale Sets

<KeyTerm term="VM Scale Set">An Azure service that lets you deploy and manage a group of identical, load-balanced Virtual Machines. Scale Sets can automatically increase or decrease the number of VM instances in response to demand or on a schedule.</KeyTerm>

Running a single VM is fine for development and testing, but production workloads usually need to handle variable traffic. If your e-commerce site gets 10x normal traffic during a holiday sale, a single VM will buckle under the load. VM Scale Sets solve this problem by treating your VMs as a fleet rather than individuals.

With a Scale Set, you define:

- The VM image (OS and pre-installed software)
- The instance size (CPU, memory)
- The minimum and maximum number of instances
- Auto-scale rules (e.g., "add a VM when average CPU exceeds 75%")

Scale Sets then automatically manage the fleet — spinning up new instances when load increases and terminating them when load drops — keeping your costs aligned with actual demand. All instances are identical and load-balanced, so any instance can handle any incoming request.

<Callout type="info">
Scale Sets support both **manual scaling** (you set the instance count) and **automatic scaling** (Azure adjusts the count based on metrics or schedules). They also integrate with Azure Load Balancer and Azure Application Gateway to distribute traffic evenly across instances.
</Callout>

### Availability Sets

<KeyTerm term="Availability set">A logical grouping of Virtual Machines within a data center that protects against hardware failures and planned maintenance events. Machines in an availability set are spread across multiple fault domains and update domains.</KeyTerm>

Even within a single Azure data center, hardware failures happen. A rack of servers might lose power, or a batch of servers might need a firmware update. Availability sets protect against these scenarios by ensuring your VMs aren't all sitting on the same physical hardware.

Availability sets use two concepts:

- **Fault domains** — A fault domain is a rack of servers that shares a common power supply and network switch. If that rack loses power, all servers in it go down. Placing your VMs across multiple fault domains means a single rack failure won't take all your VMs offline. Azure supports up to 3 fault domains in an availability set.

- **Update domains** — When Azure performs planned maintenance (like applying hypervisor updates), it reboots servers in controlled batches rather than all at once. An update domain is one such batch. VMs in different update domains are never rebooted simultaneously. Azure supports up to 20 update domains in an availability set.

By spreading VMs across fault domains and update domains, an availability set ensures that at least one VM remains available during both unplanned hardware failures and planned maintenance windows.

<Callout type="warning">
Availability sets protect against failures *within a single data center*. They do not protect against a full data center or regional outage. For that level of protection, you need **availability zones** (which spread resources across physically separate data centers within a region) or cross-region redundancy.
</Callout>

<DeepDive title="Choosing the Right Availability Strategy for VMs">
Azure offers three main options for making VMs highly available, each addressing a different failure scope:

**Availability Sets** (within a data center): Protect against rack-level hardware failures and planned maintenance events within a single data center. Use these when you need basic redundancy and your region doesn't support availability zones, or when cost is a primary concern (availability sets themselves are free — you only pay for the VMs).

**Availability Zones** (within a region): Protect against entire data center failures. VMs are placed in physically separate data center facilities with independent power, cooling, and networking. Azure provides a 99.99% uptime SLA when you deploy two or more VMs across two or more zones. This is the recommended approach for most production workloads in supported regions.

**VM Scale Sets with zones**: Combine automatic scaling with zone-level redundancy. Instances are distributed across availability zones, giving you both elasticity (scale up/down) and resilience (survive zone failures).

**Cross-region redundancy**: For protection against full regional failures, you can deploy VMs in a secondary region and use services like Azure Site Recovery to automate failover. This is the most expensive option but provides the highest level of protection.

For the AZ-900 exam, understand the difference between fault domains (protection within a data center) and availability zones (protection across data centers). Availability sets use fault domains; availability zones are separate facilities entirely.
</DeepDive>

## Azure App Service

<KeyTerm term="Azure App Service">A fully managed Platform as a Service (PaaS) for building, deploying, and scaling web applications, REST APIs, and mobile backends. Azure manages the underlying infrastructure — OS patching, hardware, load balancing — so you focus exclusively on your application code.</KeyTerm>

If Virtual Machines are like renting a bare apartment (you furnish it yourself), Azure App Service is like renting a fully furnished, managed apartment — the infrastructure is set up and maintained for you, and you just move in with your belongings (your code).

App Service supports a wide range of programming languages and frameworks:

- .NET and .NET Framework
- Java (Spring, Tomcat)
- Node.js
- Python (Django, Flask)
- PHP
- Ruby

Because App Service is PaaS, Azure handles:

- **Hardware and OS** — the underlying servers and their operating systems
- **OS patching** — security updates are applied automatically
- **Load balancing** — traffic is distributed across instances
- **TLS/SSL certificates** — HTTPS configuration is simplified
- **Auto-scaling** — you configure rules and Azure scales your app

You are responsible for:

- **Application code** — your business logic, APIs, and UI
- **Application configuration** — environment variables, connection strings
- **Deployment** — pushing new versions of your code

App Service integrates natively with GitHub, Azure DevOps, and other CI/CD pipelines, so code pushed to a branch can automatically trigger a deployment. It also supports **deployment slots** — separate staging environments where you can test a new version before swapping it into production with zero downtime.

<Callout type="tip">
For the exam, App Service is the go-to answer for "hosting a web app without managing infrastructure." It sits squarely in the PaaS category. The key distinction from VMs: with App Service, you have no access to the underlying OS — you can only deploy and configure your application.
</Callout>

## Container Services

Before covering Azure's container services, it helps to understand what a container is.

<KeyTerm term="Container">A lightweight, portable package that bundles an application's code together with all the libraries, configuration, and runtime dependencies it needs to run. Containers share the host operating system kernel but are isolated from each other, making them more efficient than VMs while maintaining good isolation.</KeyTerm>

Think of a container like a standardized shipping container. Before shipping containers, freight was loaded in all sorts of different ways and had to be reorganized at each port. Shipping containers standardized the box — any ship, truck, or crane can handle them the same way, regardless of what's inside. Software containers do the same thing for code: package the app and everything it needs into a standard unit that runs the same way regardless of where it's deployed.

Containers are smaller than VMs (no full OS copy per container, just the app and its dependencies), start faster (seconds vs. minutes for VMs), and run consistently across development laptops, test servers, and production cloud environments.

Azure provides three tiers of container hosting, each appropriate for different use cases.

### Azure Container Instances (ACI)

<KeyTerm term="Azure Container Instances (ACI)">The simplest and fastest way to run a container in Azure, with no orchestration overhead. You submit a container image, specify CPU and memory, and ACI starts the container within seconds. Ideal for isolated tasks, batch jobs, and simple scenarios that don't require persistent load balancing or complex networking.</KeyTerm>

ACI is Azure's "just run my container" option. There's no cluster to manage, no nodes to configure, and no scheduler to set up. You point ACI at a container image (from Azure Container Registry, Docker Hub, or another registry), specify how much CPU and memory to allocate, and within seconds your container is running.

ACI is best for:

- Short-lived or batch workloads (process a file, run a report)
- Simple isolated tasks that don't need load balancing
- Development and testing environments
- Scenarios where you need a container fast without infrastructure overhead

ACI is not designed for complex, multi-container applications that need service discovery, auto-scaling across many containers, or sophisticated networking between microservices. For those, you need Container Apps or AKS.

### Azure Container Apps

<KeyTerm term="Azure Container Apps">A serverless container platform built on Kubernetes that enables you to run microservices and containerized applications without managing the underlying infrastructure. Container Apps provides automatic scaling (including scale-to-zero), event-driven scaling, and service-to-service communication, while Azure handles all cluster operations.</KeyTerm>

Container Apps sits between the simplicity of ACI and the full power of AKS. It runs on Kubernetes under the hood, but Azure manages all the cluster operations — you never interact with Kubernetes directly.

Container Apps is particularly well-suited for:

- **Microservices** — multiple containers that communicate with each other
- **Event-driven workloads** — scale up when messages arrive in a queue, scale down when quiet
- **APIs and web services** that need HTTP ingress, auto-scaling, and revision management
- **Serverless containers** — scale to zero when idle (no traffic = no cost)

The "scale to zero" capability is a key differentiator: when no traffic is arriving, Container Apps can reduce your running containers to zero, so you pay nothing. As soon as a request arrives, it scales back up automatically.

### Azure Kubernetes Service (AKS)

<KeyTerm term="Azure Kubernetes Service (AKS)">A managed Kubernetes service that simplifies the deployment and operation of production Kubernetes clusters in Azure. AKS handles cluster provisioning, health monitoring, and upgrades, while you retain full control over cluster configuration, networking, and workload deployment.</KeyTerm>

<KeyTerm term="Kubernetes">An open-source container orchestration platform that automates the deployment, scaling, and management of containerized applications across a cluster of machines.</KeyTerm>

Kubernetes is the industry-standard platform for running complex containerized applications at scale. It handles scheduling containers onto nodes, restarting failed containers, distributing traffic, managing secrets and configuration, rolling out updates, and much more.

AKS provides a managed Kubernetes control plane — Microsoft runs and maintains the Kubernetes API server, scheduler, and etcd datastore. You manage the **worker nodes** (the VMs that actually run your containers) and all workload configuration. AKS is appropriate when:

- Your application consists of many microservices with complex networking requirements
- You need fine-grained control over Kubernetes configuration, networking policies, and resource allocation
- Your team has Kubernetes expertise and can take on cluster configuration responsibilities
- You're running large-scale, production container workloads

<Callout type="info">
A useful way to remember the three container options: **ACI** = run one container, quickly, no fuss. **Container Apps** = run microservices, managed Kubernetes, serverless scaling. **AKS** = full Kubernetes control, complex workloads, your team manages the cluster config.
</Callout>

## Azure Functions

<KeyTerm term="Azure Functions">A serverless compute service that runs individual functions of code in response to events or triggers. Azure manages all infrastructure automatically — you only write and deploy your code. Under the consumption plan, you pay only when your function executes.</KeyTerm>

Azure Functions takes the abstraction one step further than App Service. With App Service, you still deploy an entire application that runs continuously. With Functions, you deploy individual pieces of code — functions — that only run when triggered by an event.

Imagine you run an e-commerce platform. When a customer uploads a product photo, you need to:

1. Generate a thumbnail version
2. Compress and optimize the image
3. Scan it for inappropriate content
4. Update a database record

Each of these is a small, discrete task. You could build a continuous application that polls for new photos, but that would mean paying for a running server even when no photos are being uploaded. With Azure Functions, each task becomes a separate function triggered by the file upload event. The functions run, do their work, and stop — and you're charged only for the milliseconds they execute.

### Key Characteristics of Azure Functions

- **Event-driven** — Functions run in response to triggers: HTTP requests, timer schedules, messages in Azure Queue Storage or Service Bus, new blobs in Azure Storage, database changes, and many others.
- **Stateless by default** — Each function invocation is independent. If you need to maintain state across invocations, you use **Durable Functions**, an extension that adds workflow orchestration with automatic state persistence.
- **Multiple language support** — Functions can be written in C#, JavaScript/TypeScript, Python, Java, PowerShell, and others.
- **Scale automatically** — Azure scales the number of function instances up and down automatically based on the rate of incoming triggers. During a traffic spike, Azure starts more instances; when traffic drops, instances are reclaimed.
- **Consumption pricing model** — Under the consumption plan, you pay per execution and per the resources consumed during execution (measured in GB-seconds). There is a generous free tier each month.

<Callout type="tip">
For the exam, remember the key selling point of Azure Functions: **you pay only when your code runs**. This is the defining characteristic of the consumption-based serverless model — no idle costs. Compare this to a VM, which you pay for whether it's doing work or sitting idle.
</Callout>

<DeepDive title="Serverless vs. 'No Servers' — What Serverless Really Means">
"Serverless" is one of the most misunderstood terms in cloud computing. It doesn't mean there are no servers — your code runs on a server somewhere in Azure's data center. What it means is that *you* don't manage those servers.

In a traditional compute model, you provision a server (or VM), deploy your application, and keep that server running 24/7 — whether it's handling requests or sitting idle at 2 AM. You pay for the server continuously. You patch the OS. You worry about whether you have enough capacity for a traffic spike.

In a serverless model, you hand Azure your code and say "run this when X happens." Azure figures out where and how to run it, allocates exactly the resources needed for the duration of the execution, and then releases those resources. You're billed only for actual execution time, often down to the millisecond.

This model has two major implications:

1. **Cost efficiency**: Workloads with sporadic, unpredictable, or low-volume traffic are dramatically cheaper in a serverless model than on a continuously-running VM. A function that runs 100,000 times per month for 200ms each costs a few cents. A VM running all month costs tens of dollars.

2. **Operational simplicity**: No OS patches, no capacity planning, no server management. You focus entirely on business logic.

The tradeoff: serverless functions have **cold start latency** — if a function hasn't run recently, the first invocation after idle time can be slightly slower while Azure spins up the execution environment. For latency-sensitive workloads requiring guaranteed response times, a continuously-running service (App Service or Container Apps) might be more appropriate.

Durable Functions extend the serverless model with stateful workflows, letting you chain functions together, fan out to parallel executions, and aggregate results — all without managing a database or messaging infrastructure yourself.
</DeepDive>

## Azure Virtual Desktop

<KeyTerm term="Azure Virtual Desktop (AVD)">A cloud-based desktop and application virtualization service that delivers Windows desktops and applications to users on any device, from anywhere. AVD is the only cloud service offering multi-session Windows 11 and Windows 10, and integrates with existing Microsoft 365 licensing.</KeyTerm>

Most cloud compute services run server workloads. Azure Virtual Desktop takes a different approach: it delivers full Windows *desktop* experiences to end users — not just server-side applications, but the complete Windows desktop environment that knowledge workers use every day.

With AVD, users on any device (a laptop, a thin client, a tablet, even a smartphone) can connect to a full Windows 11 or Windows 10 desktop running in Azure. From the user's perspective, it feels like a local Windows PC. From the IT perspective, the actual compute runs in Azure's data center — all data stays in the cloud, desktops are centrally managed, and users can access their environment from anywhere with an internet connection.

### Key Characteristics of Azure Virtual Desktop

- **Multi-session Windows** — AVD is the only cloud service that supports Windows 11 and Windows 10 multi-session, where multiple users simultaneously share a single VM instance running a desktop OS (not a server OS like Windows Server). This is unique to Azure and significantly reduces licensing and infrastructure costs compared to traditional Virtual Desktop Infrastructure (VDI).
- **Centralized management** — All desktops and applications are managed centrally in Azure. Administrators manage one fleet of VMs rather than thousands of individual endpoint devices.
- **Bring your own device** — Users can connect from any device that supports the Microsoft Remote Desktop client, which is available for Windows, macOS, iOS, Android, and web browsers.
- **Microsoft 365 integration** — AVD is included with many existing Microsoft 365 plans, meaning eligible customers may not need additional licensing.
- **Security and compliance** — Data never leaves Azure's data centers. If a user's laptop is lost or stolen, no corporate data is at risk because it wasn't stored on the device.

<Callout type="info">
A useful scenario for AVD: a company wants to give remote workers access to line-of-business applications that run on Windows but doesn't want to manage physical PCs distributed across employees' homes. AVD lets everyone connect to a centrally managed Windows desktop in Azure, from whatever device they already own.
</Callout>

## Comparing Azure Compute Services

| Service | Type | You Manage | Best For |
|---|---|---|---|
| **Virtual Machines** | IaaS | OS, patches, software, security | Lift-and-shift, custom OS config, legacy apps |
| **VM Scale Sets** | IaaS | Same as VMs | Auto-scaling identical VM fleets under variable load |
| **Availability Sets** | IaaS feature | Same as VMs | HA within a data center; fault/update domain protection |
| **App Service** | PaaS | App code, configuration, deployments | Web apps, REST APIs, mobile backends without managing OS |
| **Azure Container Instances** | Containers (simple) | Container image and config | Single containers, quick isolated tasks, batch jobs |
| **Azure Container Apps** | Containers (serverless) | Container images, scaling rules | Microservices, event-driven workloads, scale-to-zero |
| **Azure Kubernetes Service** | Containers (full) | Cluster config + workloads | Complex multi-container apps requiring full Kubernetes control |
| **Azure Functions** | Serverless | Your code only | Event-driven tasks, sporadic workloads, pay-per-execution |
| **Azure Virtual Desktop** | Desktop virtualization | Desktop images, user access | Remote Windows desktops, BYOD environments, centralized VDI |

<KeyTakeaways>
- **Azure compute** is the spectrum of services that provide processing power in the cloud, ranging from full OS control (VMs) to managed platforms (App Service) to serverless (Functions).
- **Virtual Machines** are IaaS — you manage the OS, patches, and software. Best for lift-and-shift migrations, legacy apps, and workloads requiring direct OS access.
- **VM Scale Sets** automatically scale a fleet of identical VMs based on demand metrics or schedules. All instances are load-balanced and interchangeable.
- **Availability sets** protect against hardware failures and planned maintenance within a data center using **fault domains** (separate power/networking racks) and **update domains** (batches for rolling updates).
- **Azure App Service** is PaaS — you deploy code, Azure manages OS, patching, and infrastructure. Supports .NET, Java, Node.js, Python, PHP, and Ruby with built-in CI/CD and auto-scaling.
- **Containers** bundle an app with its dependencies for consistent, portable deployment. Azure offers three tiers: ACI (simple, single container), Container Apps (serverless microservices, scale-to-zero), and AKS (full Kubernetes for complex workloads).
- **Azure Functions** is serverless and event-driven — write code, define a trigger, pay only when it runs. Stateless by default; Durable Functions adds stateful workflow support.
- **Azure Virtual Desktop** delivers full Windows desktop experiences to any device from anywhere. It is the only cloud service offering multi-session Windows 10/11, and integrates with existing Microsoft 365 licenses.
- The core tradeoff across all compute services: more control (VMs) vs. more managed (Functions). Choose based on how much OS and infrastructure management responsibility your team wants to retain.
</KeyTakeaways>
