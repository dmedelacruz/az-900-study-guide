## What is the Shared Responsibility Model?

When you move workloads to the cloud, you don't simply hand everything over to Microsoft and walk away. Security and operational duties are split between you and the cloud provider — and understanding exactly where that line falls is critical for both the AZ-900 exam and real-world cloud deployments.

<KeyTerm term="Shared Responsibility Model">A framework that defines which security and operational tasks are managed by the cloud provider, which are managed by the customer, and which are shared — with the exact division depending on the type of cloud service in use.</KeyTerm>

Think of it like renting an apartment. Your landlord is responsible for maintaining the building's structure, the plumbing, the electrical systems, the lobby security cameras, and the locks on the main entrance. But securing your own belongings, setting the deadbolt on your front door every night, and deciding who gets a spare key? That's entirely on you. The landlord cannot be held responsible if you lend your key to someone who steals your laptop.

Cloud computing works the same way. Microsoft Azure owns and secures the physical infrastructure — the data centers, the servers, the networking cables, the power supply. But you own your data, your user accounts, and your access policies. Between those two extremes lies a middle zone where responsibility shifts depending on the type of service you choose.

<Callout type="info">
The shared responsibility model isn't just a conceptual framework — it has direct implications for compliance and security audits. When an organization undergoes a SOC 2 or ISO 27001 audit in the cloud, auditors expect clear documentation of which controls are Azure's responsibility and which are the customer's. Understanding this model is essential for compliance teams as much as it is for the exam.
</Callout>

## The Two Anchors: What Never Changes

Before looking at where responsibility shifts, it helps to understand what is fixed regardless of which cloud service model you use.

**Always Microsoft's responsibility — the physical layer:**

- **Physical datacenter** — The building, fencing, guards, badge readers, and surveillance cameras that protect the facility.
- **Physical network** — The fiber, switches, routers, and cables connecting Microsoft's global infrastructure.
- **Physical hosts** — The actual servers, CPUs, and storage hardware inside the data center.

Azure controls these layers completely. You have no ability to configure them, and no obligation to secure them. If a hard drive fails in a Microsoft data center, that's Microsoft's problem to fix.

**Always your responsibility — the data and identity layer:**

- **Information and data** — The content you store in the cloud, whether it's database records, files, or application state. Microsoft does not read or manage your data for you.
- **Devices and endpoints** — The laptops, phones, and workstations your users connect from. If an employee's laptop is compromised, that's outside Azure's responsibility.
- **Accounts and access management** — Who has permission to access your Azure resources and what they're allowed to do. Microsoft provides the tools (Microsoft Entra ID, role-based access control), but configuring them correctly is your job.

<Callout type="warning">
A common misconception: many organizations assume that because their data is stored in Azure, Microsoft is responsible for protecting it. This is incorrect. Microsoft secures the infrastructure that holds your data — but the data itself, including how it's encrypted, who can access it, and how it's backed up, remains your responsibility regardless of which service model you use.
</Callout>

## How Responsibility Shifts by Service Type

The middle layers — operating system, network controls, applications, and middleware — are where the three cloud service models diverge. Each model represents a different point on the responsibility spectrum.

### IaaS — Infrastructure as a Service

<KeyTerm term="Infrastructure as a Service (IaaS)">A cloud model where the provider delivers virtualized computing infrastructure (servers, storage, networking) over the internet, while the customer is responsible for the operating system, middleware, applications, and data.</KeyTerm>

IaaS is the "bare land lease" of cloud computing. Microsoft hands you a virtual machine — essentially a blank computer running in their data center — and you take it from there. You install the operating system, you patch it, you configure the firewall rules, you deploy your application, and you manage your data. The physical hardware underneath is Azure's concern, but everything above it is yours.

A typical IaaS scenario: a company lifts an existing Windows Server application to Azure by creating a virtual machine. Azure manages the physical host that VM runs on, but the company's IT team is responsible for keeping Windows updated, hardening the OS configuration, and managing who can log in via Remote Desktop.

### PaaS — Platform as a Service

<KeyTerm term="Platform as a Service (PaaS)">A cloud model where the provider manages the underlying infrastructure and runtime environment, allowing customers to focus on building and deploying applications without worrying about OS patching, middleware, or server management.</KeyTerm>

PaaS is the "furnished apartment." Microsoft provides not just the hardware but also the operating system, the runtime environment, and the middleware. You bring your application code and your data — Azure handles the platform beneath it.

Azure App Service is a classic example. You deploy your web application's code; Azure handles OS patching, load balancing, and runtime updates. You don't even know (or need to know) which physical servers your code runs on. Network controls become shared — you configure virtual network integration, but Azure manages the underlying network infrastructure.

### SaaS — Software as a Service

<KeyTerm term="Software as a Service (SaaS)">A cloud model where the provider delivers a fully managed application over the internet. The customer simply uses the software; the provider handles everything from infrastructure to application updates.</KeyTerm>

SaaS is the "hotel room." Almost everything is managed for you — the building, the furniture, the linens, the housekeeping. You're responsible for your personal belongings and for deciding who gets a key card. Microsoft 365 (formerly Office 365) is the defining SaaS example on the AZ-900 exam: Microsoft manages the application, the infrastructure, and the updates. You manage your users, your data, and your access policies.

<DeepDive title="The Spectrum of Control vs. Convenience">
There's a deliberate tradeoff baked into each service model:

**IaaS** gives you maximum control and maximum flexibility — at the cost of maximum responsibility. You can customize the OS, install any software you want, and tune network configurations to your exact specifications. But you're also on the hook for patching that OS, managing that software, and maintaining those configurations. This model suits organizations with specialized requirements, compliance needs that demand control over the OS layer, or teams with strong infrastructure expertise.

**PaaS** strikes a balance. You lose some control over the underlying stack, but you gain developer velocity. Your team can focus entirely on application logic rather than infrastructure management. The tradeoff is that you accept Azure's choices about the runtime environment — you can't necessarily install arbitrary OS packages or modify kernel settings.

**SaaS** maximizes convenience at the cost of control. Microsoft 365 does exactly what Microsoft designed it to do; you cannot modify its underlying architecture. This is appropriate for commodity workloads like email and productivity tools, but it's not suitable for highly customized enterprise applications.

Understanding this tradeoff helps you answer AZ-900 scenario questions: when a question describes a team that wants to focus on writing code without managing servers, that's PaaS. When a question describes a team that needs root-level OS access, that's IaaS.
</DeepDive>

<Callout type="tip">
For the AZ-900 exam, remember this rule of thumb: the higher up the service model ladder you go (IaaS → PaaS → SaaS), the more responsibility shifts to the provider and the less the customer needs to manage — but also the less control the customer has.
</Callout>

## The Full Responsibility Map

Here is a complete view of every layer in the cloud stack and who manages it across the three service models:

| Layer | IaaS | PaaS | SaaS |
|---|---|---|---|
| Physical datacenter | Provider | Provider | Provider |
| Physical network | Provider | Provider | Provider |
| Physical hosts | Provider | Provider | Provider |
| Operating system | **Customer** | Provider | Provider |
| Network controls | **Customer** | Shared | Provider |
| Applications | **Customer** | **Customer** | Provider |
| Identity & directory infrastructure | Shared | Shared | Shared |
| Information & data | **Customer** | **Customer** | **Customer** |
| Devices & endpoints | **Customer** | **Customer** | **Customer** |
| Accounts & access management | **Customer** | **Customer** | **Customer** |

Notice that identity, data, devices, and access management remain the customer's responsibility across all three models. These are the layers where security incidents most commonly originate — phishing attacks that steal credentials, misconfigurations that expose data publicly, or compromised endpoints that provide attackers with a foothold.

## Why the Shared Responsibility Model Matters

Understanding this model has practical consequences well beyond passing the AZ-900 exam.

**Security gaps happen at the boundary.** Most cloud security incidents don't result from Azure infrastructure failures — they result from customers misunderstanding their responsibilities. Leaving a storage container publicly accessible, using weak passwords, or failing to patch IaaS virtual machines are all customer-side failures in the shared responsibility model.

**Compliance auditors will ask.** When your organization undergoes a compliance review (SOC 2, PCI-DSS, HIPAA, ISO 27001), auditors expect you to demonstrate control over your customer-managed layers. Azure provides compliance certifications for its own infrastructure, but you must show evidence of controls on your side of the line.

**Service selection affects your security posture.** Choosing IaaS over PaaS doesn't just affect your operational workload — it expands your security surface. When you manage the OS, you're responsible for vulnerabilities in that OS. Choosing PaaS or SaaS shifts those vulnerabilities to Microsoft's side, reducing your attack surface at the cost of some control.

<DeepDive title="Shared Responsibility in the Real World: The Capital One Breach">
In 2019, Capital One suffered a data breach affecting over 100 million customers — despite hosting their workloads on a major cloud provider. The attacker exploited a misconfigured web application firewall to access AWS metadata credentials and then used those credentials to access S3 storage buckets containing customer data.

The cloud provider's physical infrastructure was never compromised. The breach occurred entirely within Capital One's responsibility domain: a misconfigured network control (their WAF) and improperly scoped access permissions for a server role. The data — always the customer's responsibility — was exposed because the customer-managed security layers were configured incorrectly.

This incident is a textbook illustration of why the shared responsibility model isn't just an exam concept. Misunderstanding where your responsibility begins is how breaches happen.
</DeepDive>

<KeyTakeaways>
- The shared responsibility model defines which cloud security and operational tasks belong to Microsoft Azure and which belong to the customer — with some layers shared between both.
- Microsoft is always responsible for the physical layers: datacenter security, physical network, and physical hosts.
- Customers are always responsible for their data, their users' devices and endpoints, and their account and access management policies — regardless of service model.
- The middle layers (OS, network controls, applications) shift based on service model: IaaS leaves the most to the customer; SaaS leaves the most to the provider.
- In IaaS, customers manage the OS and everything above it. In PaaS, the provider takes over the OS and runtime. In SaaS, the provider manages the entire application stack.
- Most cloud security incidents occur in the customer's domain — misconfigurations, weak access controls, and unpatched software are customer-side failures, not Azure failures.
- Identity and directory infrastructure is always shared: Azure runs the Entra ID platform, but configuring users, roles, and policies is the customer's job.
</KeyTakeaways>
