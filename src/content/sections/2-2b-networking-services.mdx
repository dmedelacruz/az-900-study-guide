## What Is Cloud Networking?

Every application that serves users, connects to a database, or communicates with other services relies on a network. In a traditional data center, networking means physical cables, switches, routers, and firewalls — hardware that your team purchases, configures, and maintains. In the cloud, these same networking concepts exist, but they are delivered as software-defined services that you provision and configure through the Azure portal, CLI, or templates.

Azure networking is the foundation that connects everything together: your virtual machines to each other, your cloud workloads to your on-premises data center, your applications to the internet, and your users to the services they need. Without networking, your compute and storage resources would be isolated islands with no way to communicate.

Understanding Azure networking services is essential for the AZ-900 exam. You'll need to know how virtual networks provide isolation and segmentation, how VPN Gateway and ExpressRoute connect cloud and on-premises environments, how Azure DNS manages name resolution, and how load balancers distribute traffic across your infrastructure. Let's walk through each service.

## Virtual Networks

<KeyTerm term="Azure Virtual Network (VNet)">A logically isolated network in Azure that enables Azure resources — such as VMs, databases, and app services — to securely communicate with each other, the internet, and on-premises networks. A VNet is scoped to a single Azure region and a single subscription.</KeyTerm>

Think of a VNet as your own private network within Azure's data center. Just like a corporate office has an internal network where computers can talk to each other but are isolated from the outside world by default, a VNet gives your Azure resources a private, isolated communication space.

When you create a VNet, you define an **address space** — a range of private IP addresses that the network can use. For example, you might define an address space of `10.0.0.0/16`, which provides 65,536 IP addresses for your resources. Azure resources deployed into the VNet receive private IP addresses from this range.

### Subnets

<KeyTerm term="Subnet">A subdivision of a VNet's address space that lets you segment your network into smaller, logical sections. Each subnet gets a portion of the VNet's IP range and can have its own security rules and routing configuration.</KeyTerm>

VNets are divided into **subnets** to organize and secure resources. Subnets serve the same purpose as floors in an office building — they separate different groups of resources so that you can apply different access rules to each group.

For example, a typical three-tier web application might use:

- **Web subnet** (`10.0.1.0/24`) — for the front-end web servers that accept internet traffic
- **Application subnet** (`10.0.2.0/24`) — for the middle-tier application logic, accessible only from the web subnet
- **Database subnet** (`10.0.3.0/24`) — for the database servers, accessible only from the application subnet

### Network Security Groups

<KeyTerm term="Network Security Group (NSG)">A set of security rules that filter inbound and outbound network traffic to and from Azure resources within a VNet. NSG rules specify allowed or denied traffic based on source, destination, port, and protocol.</KeyTerm>

NSGs act as a virtual firewall for your subnets and individual network interfaces. Each rule specifies:

- **Direction** — inbound or outbound
- **Priority** — lower numbers are evaluated first (100–4096)
- **Source and destination** — IP addresses, ranges, service tags, or application security groups
- **Protocol** — TCP, UDP, ICMP, or any
- **Port range** — specific ports or ranges
- **Action** — allow or deny

Rules are evaluated in priority order. Once a matching rule is found, processing stops. This means a deny rule at priority 100 will block traffic even if an allow rule exists at priority 200.

<Callout type="tip">
For the AZ-900 exam, remember that NSGs are stateful — if you allow inbound traffic on a port, the return traffic is automatically allowed. Also remember that NSGs can be applied to both subnets and individual network interfaces, providing two layers of filtering.
</Callout>

## VNet Peering

<KeyTerm term="VNet Peering">A mechanism that connects two Azure VNets so that resources in either network can communicate with each other using private IP addresses. Traffic between peered VNets travels over the Microsoft backbone network, not the public internet.</KeyTerm>

By default, resources in different VNets cannot communicate — each VNet is an isolated network boundary. VNet peering bridges that gap by linking two VNets together so that they behave as if they were one network from a connectivity perspective.

There are two types of peering:

- **Regional peering** — connects VNets within the same Azure region. Traffic stays on the local network infrastructure.
- **Global peering** — connects VNets in different Azure regions. Traffic travels over Microsoft's private global backbone, never touching the public internet.

Peered VNets have low-latency, high-bandwidth connectivity because traffic stays entirely within Microsoft's network infrastructure. This makes peering the preferred option for connecting Azure workloads that are spread across multiple VNets.

<Callout type="warning">
VNet peering is **non-transitive**. If VNet A is peered with VNet B, and VNet B is peered with VNet C, VNet A cannot communicate with VNet C through VNet B. You would need to create a separate peering between VNet A and VNet C, or use a hub-and-spoke topology with a network virtual appliance or Azure Virtual WAN.
</Callout>

## VPN Gateway

<KeyTerm term="Azure VPN Gateway">A specific type of virtual network gateway that sends encrypted traffic between an Azure VNet and another network — an on-premises data center, another VNet, or a remote user's device — over the public internet using IPsec/IKE tunnels.</KeyTerm>

VPN Gateway is your encrypted bridge between Azure and everywhere else. While VNet peering connects Azure VNets to each other, VPN Gateway extends your network to locations outside Azure — most commonly your on-premises data center.

Think of it as a secure tunnel dug under a public road. The road (the internet) is shared by everyone, but your tunnel is private and encrypted — no one else can see or intercept the traffic flowing through it.

VPN Gateway supports three connection types:

### Site-to-Site (S2S)

Connects your entire on-premises network to an Azure VNet. This creates a permanent, always-on encrypted tunnel between your on-premises VPN device (a physical router or firewall) and the Azure VPN Gateway. All resources on both sides can communicate as if they were on the same network.

**Use case:** A company wants its Azure VMs to access an on-premises file server, and its on-premises users to access applications running in Azure.

### Point-to-Site (P2S)

Connects an individual client device (a laptop, desktop, or mobile device) to an Azure VNet. Instead of linking an entire network, P2S creates a VPN tunnel from a single device. Each user installs a VPN client and establishes a connection on demand.

**Use case:** Remote employees working from home need to access Azure-hosted resources securely without a corporate VPN concentrator at each location.

### VNet-to-VNet

Connects two Azure VNets through encrypted VPN tunnels. While VNet peering is generally preferred for Azure-to-Azure connectivity (it's faster and simpler), VNet-to-VNet VPN connections are useful when you need encryption between the VNets or when connecting VNets across different Microsoft Entra ID tenants.

<DeepDive title="VPN Gateway SKUs and Performance">
Azure VPN Gateway comes in several SKUs (pricing tiers) that determine the number of tunnels, aggregate throughput, and features available:

**Basic** — Suitable for development and testing. Supports only route-based VPN with limited throughput (~100 Mbps). Does not support point-to-site with IKEv2 or RADIUS authentication. Not recommended for production.

**VpnGw1–VpnGw5** — Production SKUs with increasing throughput (from 650 Mbps to 10 Gbps) and tunnel counts. Higher SKUs support more site-to-site tunnels and higher point-to-site connection counts.

**VpnGw1AZ–VpnGw5AZ** — Availability-zone-aware versions of the production SKUs. These deploy the gateway across availability zones for higher resilience against data center-level failures.

For the AZ-900 exam, you don't need to memorize specific SKU details. What matters is understanding that VPN Gateway provides encrypted connectivity over the public internet, and that throughput and features scale with the SKU tier you choose.
</DeepDive>

## Azure ExpressRoute

<KeyTerm term="Azure ExpressRoute">A service that creates a private, dedicated connection between your on-premises infrastructure and Azure, bypassing the public internet entirely. ExpressRoute connections are established through a connectivity provider at a colocation facility and offer higher bandwidth, lower latency, and greater reliability than VPN connections.</KeyTerm>

If VPN Gateway is a secure tunnel under a public road, ExpressRoute is a private highway built exclusively for your traffic. Your data never travels over the public internet — it flows through a dedicated, private connection between your data center and Azure.

ExpressRoute is designed for organizations that need:

- **Higher bandwidth** — ExpressRoute supports connections from 50 Mbps to 100 Gbps, far exceeding what VPN Gateway can deliver.
- **Lower and more predictable latency** — because traffic doesn't traverse the unpredictable public internet, latency is consistent and low.
- **Higher reliability** — ExpressRoute connections include built-in redundancy with active-active connectivity through two independent circuits.
- **Access to all Azure services** — ExpressRoute provides connectivity to Azure public services (Storage, SQL Database) and Microsoft 365 without routing through the internet.

<Callout type="info">
ExpressRoute does **not** encrypt traffic by default — it's a private connection, so encryption is not inherently needed in the same way as a VPN tunnel over the internet. However, you can layer VPN encryption on top of ExpressRoute if your compliance requirements demand it.
</Callout>

### How ExpressRoute Works

You don't run a cable directly from your office to an Azure data center. Instead, you work with a **connectivity provider** (such as AT&T, Equinix, or Megaport) that has a physical presence in both your data center region and an Azure peering location. The provider establishes the private link, and you connect to the provider's network.

There are three connectivity models:

- **Colocation at a cloud exchange** — if your data center is colocated at a facility that also hosts Azure, you can request a cross-connect through the exchange.
- **Point-to-point Ethernet** — a dedicated Ethernet link from your facility to Azure through the provider.
- **Any-to-any (IPVPN)** — integrate Azure into your existing MPLS/WAN network through the provider.

<DeepDive title="ExpressRoute vs. VPN Gateway — When to Use Which">
Both services connect on-premises networks to Azure, but they serve different needs:

| Factor | VPN Gateway | ExpressRoute |
|---|---|---|
| **Connection type** | Encrypted tunnel over public internet | Private, dedicated link bypassing internet |
| **Bandwidth** | Up to ~10 Gbps (VpnGw5) | Up to 100 Gbps |
| **Latency** | Variable (depends on internet conditions) | Predictable and low |
| **Cost** | Lower — requires only a VPN device on-premises | Higher — requires a connectivity provider contract |
| **Setup time** | Minutes to hours | Days to weeks (provider provisioning) |
| **Encryption** | Built-in (IPsec) | Not encrypted by default (can add VPN on top) |
| **Best for** | Small-to-medium workloads, dev/test, backup connectivity | Mission-critical production, large data transfers, low-latency requirements |

**Choose VPN Gateway** when cost is a priority, workloads are moderate, or you need a quick connection. It's also commonly used as a backup path alongside ExpressRoute.

**Choose ExpressRoute** when your organization needs guaranteed bandwidth, low latency for real-time workloads (like SAP or large database replication), or when regulatory requirements prohibit traffic flowing over the public internet.

Many enterprises use both: ExpressRoute as the primary connection and VPN Gateway as a failover path.
</DeepDive>

## Azure DNS

<KeyTerm term="Azure DNS">A hosting service for DNS domains that provides name resolution using Microsoft Azure infrastructure. Azure DNS lets you manage DNS records for your domains using the same Azure tools, credentials, billing, and support contracts as your other Azure services.</KeyTerm>

The Domain Name System (DNS) is often called the "phone book of the internet." When a user types `www.contoso.com` into their browser, DNS translates that human-readable name into an IP address like `40.76.4.15` that computers use to route traffic. Without DNS, users would have to memorize IP addresses to visit websites.

Azure DNS lets you host your DNS zones in Azure, managing all your DNS records (A, AAAA, CNAME, MX, TXT, and others) alongside your other Azure resources. This provides several advantages:

- **Reliability and performance** — Azure DNS runs on Microsoft's global network of name servers, providing high availability through Anycast networking. Queries are answered by the closest server, minimizing latency.
- **Integrated management** — manage DNS records using the Azure portal, Azure CLI, PowerShell, REST API, or ARM templates — the same tools you use for everything else in Azure.
- **RBAC and activity logs** — control who can modify DNS records using Azure role-based access control, and track every change through Azure activity logs.
- **Private DNS zones** — Azure DNS also supports private DNS zones for name resolution within your VNets, so your internal resources can use human-readable names without exposing them to the internet.

<Callout type="warning">
Azure DNS is a DNS **hosting** service, not a domain **registrar**. You cannot purchase a domain name through Azure DNS. You buy your domain from a registrar (like GoDaddy, Namecheap, or Azure App Service Domains), then point the domain's name servers to Azure DNS for hosting and record management.
</Callout>

## Azure Load Balancer

<KeyTerm term="Azure Load Balancer">A Layer 4 (transport layer) load-balancing service that distributes incoming network traffic across multiple backend resources, such as VMs, based on source IP, source port, destination IP, destination port, and protocol. It provides high availability by routing traffic only to healthy instances.</KeyTerm>

When your application runs on multiple VMs or instances, you need a way to distribute incoming traffic evenly across them. If all traffic hits a single instance, it becomes a bottleneck and a single point of failure. A load balancer solves both problems: it spreads traffic across multiple instances and stops sending traffic to any instance that becomes unhealthy.

Azure Load Balancer operates at **Layer 4** of the OSI model — the transport layer. This means it makes routing decisions based on network-level information: IP addresses, ports, and protocols (TCP/UDP). It does not inspect the content of the traffic (HTTP headers, URLs, cookies) — that's the job of Application Gateway (Layer 7).

### Public vs. Internal Load Balancer

- **Public Load Balancer** — has a public IP address and distributes incoming internet traffic across your backend VMs. This is what you use when users on the internet need to reach your application.
- **Internal (Private) Load Balancer** — has only a private IP address and distributes traffic within your VNet. This is used for internal workloads — for example, load-balancing traffic between your web tier and your application tier, where no internet-facing access is needed.

### Health Probes

Load Balancer uses **health probes** to determine which backend instances are healthy. A health probe sends periodic checks (HTTP, HTTPS, or TCP) to each instance. If an instance fails to respond within a configured threshold, Load Balancer stops sending traffic to it until it recovers.

<Callout type="tip">
For the AZ-900 exam, remember the key distinction: Azure Load Balancer works at **Layer 4** (TCP/UDP — network level). It does not understand HTTP, URLs, or application-level routing. If you need URL-based routing, SSL termination, or Web Application Firewall capabilities, that's **Application Gateway** (Layer 7).
</Callout>

## Application Gateway

<KeyTerm term="Azure Application Gateway">A Layer 7 (application layer) load balancer that manages traffic to web applications. It makes routing decisions based on HTTP attributes such as URI path, host headers, and cookies, and includes features like SSL/TLS termination, URL-based routing, and an optional Web Application Firewall (WAF).</KeyTerm>

Application Gateway is Azure's HTTP-aware load balancer. While Azure Load Balancer routes traffic based on IP addresses and ports, Application Gateway understands the content of web requests and makes intelligent routing decisions based on that content.

Key capabilities:

- **URL-based routing** — route requests to different backend pools based on the URL path. For example, `/images/*` goes to an image server pool, and `/api/*` goes to an API server pool.
- **Multi-site hosting** — host multiple websites behind a single Application Gateway instance, routing traffic based on the host header (e.g., `app1.contoso.com` vs. `app2.contoso.com`).
- **SSL/TLS termination** — decrypt HTTPS traffic at the gateway so backend servers don't need to handle encryption overhead. The gateway can also re-encrypt traffic for end-to-end SSL if required.
- **Cookie-based session affinity** — ensure that a user's requests are always routed to the same backend server, which is useful for applications that store session state locally.
- **Web Application Firewall (WAF)** — an optional feature that protects web applications from common exploits like SQL injection, cross-site scripting (XSS), and other OWASP Top 10 vulnerabilities.

<Callout type="info">
Think of it this way: **Load Balancer** is a traffic cop directing cars at an intersection based on which lane they're in (IP/port). **Application Gateway** is a receptionist in a building lobby who reads your appointment slip (HTTP request) and directs you to the right floor and office (backend pool).
</Callout>

## Comparing Azure Networking Services

| Service | Layer | Purpose | Best For |
|---|---|---|---|
| **Virtual Network (VNet)** | Foundation | Isolated private network for Azure resources | All Azure deployments needing network isolation |
| **VNet Peering** | Connectivity | Connect VNets via Microsoft backbone | Azure-to-Azure VNet communication |
| **VPN Gateway** | Hybrid | Encrypted tunnel over public internet | On-premises to Azure, dev/test, backup path |
| **ExpressRoute** | Hybrid | Private dedicated link bypassing internet | Mission-critical, high bandwidth, low latency |
| **Azure DNS** | Name resolution | Host and manage DNS records | Domain name management within Azure |

<KeyTakeaways>
- **Azure Virtual Network (VNet)** is an isolated private network in Azure. It uses address spaces and subnets to segment resources, with Network Security Groups (NSGs) filtering traffic based on rules.
- **VNet Peering** connects two VNets over the Microsoft backbone — supporting both regional and global peering. Peering is **non-transitive**: A↔B and B↔C does not mean A↔C.
- **VPN Gateway** creates encrypted IPsec tunnels over the public internet. It supports site-to-site (whole network), point-to-site (single device), and VNet-to-VNet connections.
- **Azure ExpressRoute** provides a private, dedicated connection to Azure through a connectivity provider — higher bandwidth (up to 100 Gbps), lower latency, and traffic never crosses the public internet. It does not encrypt by default.
- **Azure DNS** hosts DNS zones and manages DNS records within Azure. It is a hosting service, **not** a domain registrar.
- **Azure Load Balancer** is a Layer 4 (TCP/UDP) load balancer that distributes traffic based on IP, port, and protocol. It comes in public (internet-facing) and internal (private) variants, using health probes to route only to healthy instances.
- **Application Gateway** is a Layer 7 (HTTP) load balancer that provides URL-based routing, SSL termination, multi-site hosting, cookie affinity, and an optional Web Application Firewall (WAF).
</KeyTakeaways>
