## Azure's Infrastructure: From the Ground Up

Every application you run in Azure — a virtual machine, a database, a container — lives somewhere physical. It sits on a real server, in a real data center, plugged into a real power grid, in a real geographic location. Understanding how Azure organizes this physical and logical infrastructure is foundational to everything else you'll learn about the platform.

Think of it like the geography of a country. A **country** contains **states or provinces**, which contain **cities**, which contain **buildings** where people actually live and work. Azure's infrastructure follows a strikingly similar hierarchy: the global Azure cloud is divided into **regions**, each region can contain multiple **availability zones**, and each availability zone maps to one or more physical **data centers**. Then, layered on top of this physical structure, Azure provides a logical organization system — **management groups**, **subscriptions**, and **resource groups** — that helps you organize, govern, and pay for everything you build.

Let's walk through both the physical and logical layers.

## Azure's Physical Infrastructure

### Regions

<KeyTerm term="Azure region">A geographic area containing one or more data centers that are networked together with a low-latency network. Azure has more than 60 regions across more than 140 countries, making it the most globally distributed cloud provider.</KeyTerm>

When you deploy a resource in Azure — say, a virtual machine — you choose a region where that resource will physically reside. The region you pick matters for several reasons:

- **Latency** — Users get faster response times when resources are deployed in a region close to them. A web application serving customers in Tokyo should run in the Japan East region, not in West US.
- **Compliance and data residency** — Many countries and industries have laws requiring data to stay within specific geographic boundaries. Deploying to a region within that boundary helps satisfy those requirements.
- **Service availability** — Not all Azure services are available in every region. Some newer or specialized services launch in a subset of regions first before expanding.
- **Pricing** — The cost of the same resource can vary between regions due to differences in local infrastructure costs, energy prices, and market conditions.

<Callout type="tip">
For the AZ-900 exam, remember that a region is a *geographic area* — not a single data center. A region typically contains multiple data centers. When you deploy a resource to "East US," Azure places it in one of several data centers within that region.
</Callout>

### Availability Zones

<KeyTerm term="Availability zone">A physically separate data center within an Azure region, equipped with independent power, cooling, and networking. Regions that support availability zones have a minimum of three zones, ensuring that a failure in one zone doesn't affect workloads running in another.</KeyTerm>

Availability zones exist to solve a critical problem: what happens if a single data center goes down? A power outage, a cooling failure, a network disruption — any of these could take an entire data center offline. If all your resources sit in one data center, your application goes down with it.

Availability zones protect against this by spreading data centers far enough apart within a region that a localized disaster (a fire, a flood, a power grid failure) is unlikely to affect more than one zone, yet close enough together that they can communicate with extremely low latency. Each zone has its own:

- **Power supply** — independent electrical feeds
- **Cooling systems** — separate HVAC infrastructure
- **Network connections** — dedicated fiber links

By deploying resources across multiple availability zones within the same region, you achieve high availability. If Zone 1 goes down, your resources in Zones 2 and 3 keep running.

<Callout type="warning">
Not all Azure regions support availability zones. Regions without availability zones still have multiple data centers, but Azure doesn't guarantee the same level of physical separation. For workloads requiring the highest availability guarantees, choose a region that supports availability zones.
</Callout>

Azure services use availability zones in two ways:

- **Zonal services** — You pin the resource to a specific zone (e.g., a VM in Zone 2). You manage redundancy yourself by deploying additional instances in other zones.
- **Zone-redundant services** — Azure automatically replicates across zones for you (e.g., zone-redundant storage automatically maintains copies in three zones).

### Region Pairs

<KeyTerm term="Region pair">Two Azure regions within the same geography that are paired together for disaster recovery purposes. Paired regions are at least 300 miles (480 km) apart, and Azure coordinates planned maintenance and recovery priorities between them.</KeyTerm>

Availability zones protect against data center failures within a region, but what if an entire region goes down — a massive earthquake, a regional power grid failure, or a catastrophic network event? Region pairs address this scenario.

Azure pairs most regions with another region in the same geography (e.g., East US is paired with West US, North Europe with West Europe). These pairs provide several benefits:

- **Geographic separation** — At least 300 miles apart, reducing the likelihood that a natural disaster affects both regions simultaneously.
- **Sequential updates** — Azure rolls out planned maintenance to one region in a pair at a time, never both simultaneously. This prevents a bad update from taking down both regions.
- **Recovery priority** — In a widespread outage affecting multiple regions, Azure prioritizes restoring one region from each pair first, ensuring every pair has at least one functional region.
- **Cross-region replication** — Some services (like geo-redundant storage) automatically replicate data to the paired region for disaster recovery.

<Callout type="info">
A few regions have asymmetric pairing — for example, Brazil South is paired with South Central US (not another Brazilian region), because there was only one region in Brazil when the pair was established. Additionally, some newer regions use availability zones as their primary resiliency strategy rather than traditional pairing.
</Callout>

### Sovereign Regions

Azure operates special isolated regions designed for government and compliance scenarios where standard public Azure regions cannot meet regulatory requirements.

<Callout type="info">
**Azure Government** is a physically separate instance of Azure exclusively for US federal, state, tribal, and local government agencies and their partners. It runs in dedicated data centers within the United States, operated by screened US personnel, and meets the most stringent government compliance standards (FedRAMP High, DoD IL5, CJIS, IRS 1075, and others). Azure Government has its own portal (portal.azure.us) and its own set of service endpoints, completely isolated from commercial Azure.

**Azure China** is operated by 21Vianet, a Chinese company, rather than by Microsoft directly. This arrangement complies with Chinese regulations that require cloud services operating within China to be managed by a domestic entity. Azure China has its own portal (portal.azure.cn) and is physically and logically separated from global Azure. Data in Azure China stays within China.

These sovereign regions have their own identity systems, compliance certifications, and service catalogs, and you cannot transfer resources between sovereign and commercial Azure regions.
</Callout>

<DeepDive title="How Azure Achieves 99.99% Uptime">
Azure's high-availability architecture is built on layered redundancy — each layer protects against a different scope of failure.

**Layer 1: Hardware redundancy within a data center.** Individual servers have redundant power supplies, network interfaces, and (often) mirrored storage. If a single server fails, workloads are automatically moved to healthy hardware.

**Layer 2: Availability zones within a region.** By spreading resources across three or more independent data center facilities — each with its own power, cooling, and network — Azure protects against facility-level failures. A zone-redundant deployment can survive the complete loss of one data center.

**Layer 3: Region pairs across geographies.** For catastrophic regional events, geo-redundant replication ensures data survives in a paired region hundreds of miles away. Services like Azure Site Recovery can automate full application failover between paired regions.

**The math of nines.** A single VM in one zone offers a 99.9% SLA (roughly 8.7 hours of downtime per year). Deploying the same VM across two or more availability zones raises the SLA to 99.99% (about 52 minutes per year). Adding geo-redundant failover pushes effective availability even higher, though the exact SLA depends on the services and configuration involved.

For the AZ-900 exam, you don't need to memorize specific SLA percentages, but you should understand that each layer of redundancy (hardware → zone → region pair) protects against progressively larger failure scenarios.
</DeepDive>

## Azure's Logical Organization

While Azure's physical infrastructure determines *where* your resources run, the logical organization determines *how* you manage, govern, and pay for them. Azure provides a four-level hierarchy for organizing resources.

### Management Groups

<KeyTerm term="Management group">A container above subscriptions that lets you organize multiple Azure subscriptions into a hierarchy for unified governance. Policies and access controls applied to a management group are inherited by all subscriptions and resources within it.</KeyTerm>

Management groups solve a governance problem: when an organization has dozens or hundreds of subscriptions, applying consistent policies subscription by subscription is tedious and error-prone. Management groups let you group subscriptions together and apply policies once at the group level.

Key facts about management groups:

- Every Azure tenant gets a **root management group** at the top of the hierarchy. All other management groups and subscriptions are descendants of this root.
- Management groups can be **nested up to six levels deep** (not counting the root), allowing for granular organizational structures.
- A management group can contain other management groups or subscriptions, but each subscription can belong to only **one management group**.
- **Azure RBAC and Azure Policy** assignments on a management group cascade down to all child management groups, subscriptions, resource groups, and resources.

For example, a large enterprise might create management groups for each business unit (Marketing, Engineering, Finance), then nest management groups for environments (Production, Development) within each. A security policy applied at the top-level business unit group automatically governs every subscription and resource underneath it.

### Subscriptions

<KeyTerm term="Azure subscription">A billing and access-control boundary in Azure. Every Azure resource belongs to a subscription, and each subscription generates a separate bill. Organizations use multiple subscriptions to separate environments, departments, or billing responsibilities.</KeyTerm>

A subscription serves two critical purposes:

- **Billing boundary** — All charges for resources within a subscription appear on a single bill. An organization might create separate subscriptions for development and production so each gets its own invoice, or assign different subscriptions to different departments for cost tracking.
- **Access-control boundary** — You can apply different access policies to different subscriptions. Development teams might have broad permissions in a development subscription but restricted access in the production subscription.

Organizations create multiple subscriptions for several reasons:

- **Environment separation** — dev, test, staging, and production each in their own subscription
- **Departmental billing** — each department gets its own subscription and its own bill
- **Subscription limits** — Azure imposes per-subscription limits on certain resources (e.g., the number of virtual networks per subscription). When you approach a limit, you can create additional subscriptions.
- **Compliance isolation** — regulated workloads in a separate subscription with stricter controls

### Resource Groups

<KeyTerm term="Resource group">A logical container that holds related Azure resources. Every Azure resource must belong to exactly one resource group. Resources in a group can be in different regions. Deleting a resource group deletes all resources within it.</KeyTerm>

Resource groups are the fundamental organizational unit for Azure resources. Think of them as folders for your cloud resources — but with important rules:

- **Every resource must be in exactly one resource group.** You can't have a resource that belongs to two groups, and you can't have a resource outside of any group.
- **Resources can span regions.** A resource group might contain a VM in East US and a database in West Europe. The resource group itself has a location (for metadata storage), but the resources inside it can be anywhere.
- **Lifecycle management.** Resources in a group often share the same lifecycle — they're created together, managed together, and deleted together. Deleting a resource group deletes everything in it, making cleanup straightforward.
- **Access control scope.** You can assign RBAC roles at the resource group level, giving a team access to all resources in the group without granting access to resources in other groups.

<Callout type="tip">
A common exam question tests whether resources in a resource group must be in the same region. The answer is **no** — a resource group can contain resources from multiple regions. The resource group's own location only determines where its metadata (the list of what it contains) is stored.
</Callout>

### Azure Resource Manager (ARM)

<KeyTerm term="Azure Resource Manager (ARM)">The deployment and management service for Azure. Every request to create, update, delete, or manage an Azure resource — whether it comes from the Azure portal, Azure CLI, PowerShell, REST APIs, or SDKs — goes through ARM, which provides a consistent management layer with authentication, authorization, and auditing.</KeyTerm>

ARM is the gatekeeper for all Azure resource operations. No matter how you interact with Azure, your request passes through ARM:

- **Azure portal** → sends REST API calls to ARM
- **Azure CLI** → sends REST API calls to ARM
- **Azure PowerShell** → sends REST API calls to ARM
- **Client SDKs and REST APIs** → call ARM directly

This single entry point provides several powerful capabilities:

- **Consistent management layer** — The same operations work regardless of the tool you use. A VM created via the portal is identical to one created via the CLI.
- **Authentication and authorization** — ARM integrates with Microsoft Entra ID to authenticate every request and checks Azure RBAC to ensure the caller has permission for the operation.
- **Tagging** — ARM supports tags (key-value pairs) on resources, enabling flexible categorization for cost management, operations, and governance.
- **ARM templates and Bicep** — ARM supports declarative templates (JSON-based ARM templates or the more concise Bicep language) that define your infrastructure as code, enabling repeatable, consistent deployments.
- **Dependency management** — When deploying multiple resources that depend on each other, ARM understands the dependencies and deploys them in the correct order, parallelizing where possible.

Policies and RBAC assignments on a management group are inherited by all subscriptions and resources below it. You can nest management groups up to six levels deep (not counting the root).     Subscriptions serve as both a billing boundary and an access-control boundary. Each subscription produces a separate invoice, making it easy to track costs by department, project, or environment. Deleting a resource group deletes all resources inside it, making resource groups a convenient lifecycle management tool.

<DeepDive title="ARM Templates and Infrastructure as Code">
One of ARM's most powerful features is its support for **Infrastructure as Code (IaC)** — the practice of defining your cloud infrastructure in declarative template files rather than manually clicking through a portal.

**ARM templates** are JSON files that describe the resources you want to deploy, their configurations, and their dependencies. When you submit a template to ARM, it reads the desired state, compares it to the current state, and makes the necessary changes. Key benefits include:

- **Repeatability** — Deploy the exact same environment every time. No more "it worked on my screen" problems caused by manual configuration differences.
- **Version control** — Store templates in Git. Track changes over time. Review infrastructure changes with the same rigor as code changes.
- **Idempotency** — You can deploy the same template multiple times without creating duplicate resources. ARM will create what's missing, update what's changed, and leave what's already correct.
- **Parallel deployment** — ARM analyzes dependencies in your template and deploys independent resources simultaneously, speeding up complex deployments.

**Bicep** is Microsoft's newer, more concise language for ARM templates. It compiles down to ARM template JSON but is much easier for humans to read and write. Think of Bicep as syntactic sugar for ARM templates — same engine, friendlier syntax.

For the AZ-900 exam, you should know that ARM templates and Bicep enable declarative, repeatable deployments and that they work through the ARM management layer. You won't need to write templates on the exam.
</DeepDive>

## Comparing Organizational Concepts

| Concept | Scope | Primary Purpose | Key Rule |
|---|---|---|---|
| **Management Group** | Above subscriptions | Governance and policy at scale | Can nest up to 6 levels deep (excluding root) |
| **Subscription** | Contains resource groups | Billing boundary + access control boundary | Each resource belongs to exactly one subscription |
| **Resource Group** | Contains resources | Logical container for related resources | Every resource must be in exactly one resource group |
| **Azure Resource Manager** | All of Azure | Consistent management layer for all operations | All requests (portal, CLI, API) go through ARM |

<KeyTakeaways>
- **Azure regions** are geographic areas with one or more data centers. Choosing the right region affects latency, compliance, service availability, and cost.
- **Availability zones** are physically separate data centers within a region, each with independent power, cooling, and networking. Regions that support them have at least three zones.
- **Region pairs** are two regions in the same geography, at least 300 miles apart, with coordinated updates and disaster recovery priority.
- **Sovereign regions** (Azure Government, Azure China) are isolated instances of Azure for government and regulatory compliance, with separate portals and identity systems.
- **Management groups** provide hierarchical governance above subscriptions, supporting up to six levels of nesting. Policies and RBAC cascade downward.
- **Subscriptions** serve as both a billing boundary (separate invoices) and an access-control boundary. Organizations use multiple subscriptions to separate environments, departments, or compliance scopes.
- **Resource groups** are required containers — every resource must belong to exactly one. Resources in a group can span regions. Deleting the group deletes all resources inside it.
- **Azure Resource Manager (ARM)** is the single management layer for all Azure operations. Every request — from portal, CLI, PowerShell, or API — passes through ARM for authentication, authorization, and consistent processing.
- ARM templates and Bicep enable Infrastructure as Code — declarative, repeatable, idempotent deployments defined in version-controlled files.
- Availability zones protect against data center failures; region pairs protect against regional failures. Together they form Azure's layered high-availability strategy.
</KeyTakeaways>
