## Why Cloud Storage Matters

Every application needs somewhere to store data — documents, images, log files, messages, database records, virtual machine disks. In a traditional data center, storage means purchasing physical hard drives, configuring RAID arrays, managing backups, and planning capacity months in advance. When you run out of space, you buy more hardware. When a drive fails, you hope your redundancy strategy was sound.

Azure Storage removes that burden. It provides durable, highly available, and massively scalable cloud storage that you can provision in minutes, scale on demand, and access from anywhere in the world over HTTP or HTTPS. Microsoft manages the physical hardware, handles replication, and guarantees availability through service-level agreements.

For the AZ-900 exam, you need to understand the core Azure Storage services — Blob, Files, Queue, and Table — how storage accounts organize these services, the redundancy options that protect your data, the access tiers that optimize cost, and the migration tools that help you move data to the cloud. Let's walk through each one.

## Storage Accounts

<KeyTerm term="Azure Storage Account">A container that groups together all of your Azure Storage services — blobs, files, queues, and tables — under a single namespace. A storage account provides a unique namespace for your data that is accessible from anywhere in the world over HTTP or HTTPS.</KeyTerm>

Think of a storage account as a building that houses different departments (Blob, Files, Queue, Table). Each department operates independently, but they all share the same address and security policies. The storage account defines the settings that apply to all services within it: the redundancy level, the access tier, the network rules, and the encryption configuration.

When you create a storage account, you choose a **globally unique name** that becomes part of the URL used to access your data. For example, if your storage account is named `contosostorageacct`, your blob data would be accessible at `https://contosostorageacct.blob.core.windows.net`.

<Callout type="tip">
Storage account names have strict rules for the AZ-900 exam: they must be **3 to 24 characters** long, use only **lowercase letters and numbers** (no hyphens, no uppercase, no special characters), and must be **globally unique** across all of Azure. If someone else already has a name, you can't use it.
</Callout>

### Storage Account Types

Azure offers several storage account types, but the one you need to know for the AZ-900 exam is:

- **Standard general-purpose v2 (GPv2)** — the recommended default for most scenarios. It supports all storage services (Blob, Files, Queue, Table) and all redundancy options. It uses standard hard disk drives (HDDs) for cost-effective storage.
- **Premium** — uses solid-state drives (SSDs) for low-latency, high-throughput storage. Premium accounts are available for block blobs, file shares, or page blobs, but each premium type supports only its specific service. Premium accounts only support LRS and ZRS redundancy.

## Storage Redundancy

<KeyTerm term="Storage Redundancy">The strategy Azure uses to maintain multiple copies of your data so that it remains available and durable even when hardware failures, network outages, or natural disasters occur. Every Azure storage account replicates data automatically — you choose the level of redundancy.</KeyTerm>

Azure Storage always maintains multiple copies of your data. The question is not whether your data is replicated, but how many copies exist and where they are stored. More copies across more locations means higher durability and availability — but also higher cost.

### Primary Region Redundancy

These options keep all copies within the primary region where you created the storage account:

**Locally Redundant Storage (LRS)** replicates your data **three times within a single data center** in the primary region. It protects against drive and rack failures within that data center, but not against a data center-level disaster (fire, flood, power loss). LRS is the lowest-cost option and provides **11 nines (99.999999999%) of durability** over a given year.

**Zone-Redundant Storage (ZRS)** replicates your data across **three availability zones** in the primary region. Each availability zone is a separate physical data center with independent power, cooling, and networking. ZRS protects against a single data center going offline and provides **12 nines of durability**.

### Cross-Region Redundancy

These options add a copy of your data to a secondary region hundreds of miles away:

**Geo-Redundant Storage (GRS)** uses LRS in the primary region (3 copies in one data center), then asynchronously copies your data to a secondary region where it is again stored using LRS. This gives you **six total copies** — three in the primary region's data center and three in the secondary region's data center. GRS provides **16 nines of durability**.

**Geo-Zone-Redundant Storage (GZRS)** uses ZRS in the primary region (3 copies across 3 availability zones), then asynchronously copies to the secondary region where it is stored using LRS. This combines the availability zone protection of ZRS with the geographic protection of GRS.

<KeyTerm term="Read-Access Geo-Redundant Storage (RA-GRS)">A redundancy option that builds on GRS by adding read access to the secondary region copy. With standard GRS, the secondary copy is only used for failover. With RA-GRS, you can read data from the secondary region at any time, even when the primary region is functioning normally.</KeyTerm>

**RA-GRS** and **RA-GZRS** add read access to the secondary region. Without the "RA-" prefix, the secondary region data is only available if Microsoft initiates a failover. With RA-GRS or RA-GZRS, your application can read from the secondary endpoint at any time — useful for serving read traffic from the closest region or for read-only access during a primary region outage.

<Callout type="warning">
Replication to the secondary region is **asynchronous**. There is always a small delay (the Recovery Point Objective, or RPO) between a write to the primary region and when it appears in the secondary region. Microsoft targets an RPO of under 15 minutes, but does not guarantee a specific value. This means that in a failover, the most recent writes may not yet be available in the secondary region.
</Callout>

<DeepDive title="Choosing the Right Redundancy Option">
The right redundancy option depends on your durability requirements, availability needs, and budget:

| Option | Copies | Locations | Read from Secondary? | Best For |
|---|---|---|---|---|
| **LRS** | 3 | 1 data center | No | Dev/test, non-critical data, data that can be reconstructed |
| **ZRS** | 3 | 3 availability zones (1 region) | No | Production workloads needing high availability within a region |
| **GRS** | 6 | 2 regions (LRS + LRS) | No (failover only) | Critical data needing geographic protection |
| **GZRS** | 6 | 2 regions (ZRS + LRS) | No (failover only) | Highest durability: zone + geo protection |
| **RA-GRS** | 6 | 2 regions (LRS + LRS) | Yes | Read-heavy apps wanting secondary region reads |
| **RA-GZRS** | 6 | 2 regions (ZRS + LRS) | Yes | Maximum availability and durability |

For the AZ-900 exam, remember: LRS = cheapest/least durable (single data center), ZRS = zone-level protection, GRS/GZRS = geographic protection, and the "RA-" prefix means you can read from the secondary region without waiting for a failover.
</DeepDive>

## Blob Storage

<KeyTerm term="Azure Blob Storage">An object storage service optimized for storing massive amounts of unstructured data — data that does not conform to a particular data model or definition, such as text files, images, videos, logs, backups, and binary data. "Blob" stands for Binary Large Object.</KeyTerm>

Blob storage is Azure's most versatile storage service. It is designed for storing any type of unstructured data — anything that doesn't fit neatly into rows and columns. Think of it as an infinitely expandable file cabinet where you can toss in any type of file: photos, videos, documents, log files, database backups, virtual machine disk images, or raw sensor data from IoT devices.

Blob storage organizes data into **containers**, which function like folders. A storage account can have unlimited containers, and each container can hold unlimited blobs. Containers provide a grouping level for security and organization — you can set access policies at the container level.

### Blob Types

Azure Blob Storage supports three types of blobs, each optimized for different scenarios:

- **Block blobs** — store text and binary data, up to about 190.7 TiB. Data is uploaded in blocks that are then committed as a whole blob. Block blobs are the default and most common type, ideal for documents, images, videos, and any file you'd upload and download as a unit.
- **Append blobs** — optimized for append operations. New data can only be added to the end of the blob, not modified or inserted in the middle. This makes append blobs ideal for logging scenarios where data is continuously written but never modified.
- **Page blobs** — store random-access files up to 8 TiB. Data is stored in 512-byte pages that can be read and written individually. Page blobs are the foundation for Azure Virtual Machine disks (VHDs) — every Azure VM's OS disk and data disk is backed by page blobs.

<Callout type="info">
For the AZ-900 exam, remember these blob type associations: **block blobs** for general-purpose file storage, **append blobs** for log files and streaming data, and **page blobs** for VM disks. You don't need to memorize size limits, but knowing the use case for each type is important.
</Callout>

## Azure Files

<KeyTerm term="Azure Files">A fully managed file share service that offers industry-standard SMB (Server Message Block) and NFS (Network File System) file shares accessible from the cloud or on-premises. Azure file shares can be mounted concurrently by cloud or on-premises deployments of Windows, Linux, and macOS.</KeyTerm>

Azure Files brings traditional network file shares to the cloud. If you've ever mapped a network drive at work to access shared documents on a file server, Azure Files provides the same experience — but the file server is managed by Microsoft in the cloud.

The key advantage of Azure Files is **protocol compatibility**. It supports the same SMB and NFS protocols that on-premises file servers use, so existing applications that read from or write to network file shares can switch to Azure Files without code changes. Just change the file share path and your application continues working as before.

Common use cases for Azure Files:

- **Lift-and-shift migrations** — when migrating applications that depend on file shares, Azure Files provides a drop-in replacement without rewriting the application to use Blob storage APIs.
- **Shared configuration files** — store configuration files in a central Azure file share accessible by multiple VMs or application instances.
- **Diagnostic data** — centralize log files, crash dumps, and metrics from multiple sources into a shared file location.
- **Development tools and utilities** — share development tools, scripts, and utilities across team members and build agents.

### Azure File Sync

Azure File Sync extends Azure Files to your on-premises Windows Server, letting you cache frequently accessed files locally while keeping the full data set in the cloud. This turns your Windows Server into a fast local cache of your Azure file share — frequently used files are accessed at local speed, while rarely used files are tiered to the cloud and recalled on demand.

## Queue Storage

<KeyTerm term="Azure Queue Storage">A messaging service for storing large numbers of messages that can be accessed from anywhere via authenticated HTTP or HTTPS calls. Individual messages can be up to 64 KiB in size, and a queue can contain millions of messages, up to the total capacity of the storage account.</KeyTerm>

Queue storage provides a simple, reliable messaging mechanism for asynchronous communication between application components. When one part of your application produces work faster than another part can process it, a queue acts as a buffer — the producer adds messages to the queue, and the consumer retrieves and processes them at its own pace.

Think of it as a line at a restaurant. When customers arrive faster than the kitchen can cook, they wait in line (the queue). The kitchen processes orders one at a time, and the line absorbs the burst of arrivals. Without the queue, customers would be turned away during peak times.

Common patterns:

- **Work decoupling** — a web front-end adds a message to the queue for each user request, and a background worker processes them independently. If the worker goes down, messages remain in the queue and are processed when the worker recovers.
- **Load leveling** — smooth out bursts of incoming traffic by queuing requests during peak times and processing them steadily.
- **Order processing** — e-commerce applications can queue order confirmations, payment processing, and shipping notifications as independent messages.

## Table Storage

<KeyTerm term="Azure Table Storage">A NoSQL key-value store for structured, non-relational data. It stores large amounts of structured data without the complexity of a traditional relational database, using a schema-less design where each entity (row) can have a different set of properties (columns).</KeyTerm>

Table storage is Azure's simple NoSQL data store. Unlike a relational database with a fixed schema (every row must have the same columns), Table storage uses a flexible, schema-less design. Each entity (row) in a table can have completely different properties (columns) from other entities in the same table.

Data is organized using a **partition key** and a **row key**. The partition key groups related entities together for efficient querying, and the row key uniquely identifies each entity within a partition. Together, the partition key and row key form the unique identifier for every entity.

Table storage is ideal for:

- **Web application user data** — user profiles, preferences, and session data
- **Device telemetry** — IoT sensor readings and device metadata
- **Address books and contact information** — flexible schemas accommodate varying levels of detail
- **Any structured data** that does not need complex joins, foreign keys, or stored procedures

<Callout type="info">
Azure Table Storage is a cost-effective option for structured, non-relational data. For applications that need richer querying, global distribution, or guaranteed throughput, consider **Azure Cosmos DB**, which offers a Table API that is compatible with Table storage code but provides additional capabilities like turnkey global distribution and single-digit-millisecond reads.
</Callout>

## Access Tiers

<KeyTerm term="Access Tiers">Storage pricing levels that let you optimize costs based on how frequently your data is accessed. Azure Blob Storage offers four access tiers: Hot, Cool, Cold, and Archive. Each tier balances storage cost against access cost — storing data is cheaper in cooler tiers, but retrieving it is more expensive.</KeyTerm>

Not all data is accessed equally. A company's current month of sales records might be accessed hundreds of times a day, while audit logs from five years ago might never be accessed again unless there is a compliance review. Storing both at the same price tier wastes money.

Azure access tiers let you match storage costs to access patterns:

| Tier | Use Case | Min Retention | Storage Cost | Access Cost |
|---|---|---|---|---|
| **Hot** | Frequently accessed data | None | Highest | Lowest |
| **Cool** | Infrequently accessed data, short-term backup | 30 days | Lower | Higher |
| **Cold** | Rarely accessed data, long-term backup | 90 days | Lower still | Higher still |
| **Archive** | Archival data accessed almost never | 180 days | Lowest | Highest |

<KeyTerm term="Archive Tier">The lowest-cost storage tier for data that is rarely accessed and stored for at least 180 days. Data in the Archive tier is stored offline and must be rehydrated (moved to an online tier such as Hot or Cool) before it can be read. Rehydration can take up to 15 hours with standard priority.</KeyTerm>

The **Hot** tier is the default for new storage accounts. You pay more per gigabyte of stored data, but reads and writes are cheap. This is optimal for data that is actively used — web content, current documents, application data.

The **Cool** tier reduces storage costs by about 30-40% compared to Hot, but charges more for each read and write operation. Data should stay in Cool for at least 30 days — deleting or moving it earlier incurs an early deletion charge.

The **Cold** tier further reduces storage costs compared to Cool, with even higher access costs. Data should stay for at least 90 days.

The **Archive** tier offers the lowest storage costs of all — but data is stored **offline**. You cannot read a blob directly from Archive. You must first **rehydrate** it by changing its tier to Hot or Cool, which can take up to 15 hours with standard priority (or within an hour with high priority rehydration). Archive is ideal for regulatory compliance data, long-term backups, and raw data that you want to preserve but rarely need.

<Callout type="tip">
The access tier can be set at the **account level** (applies to all blobs that don't have an explicit tier) and at the **individual blob level** (overrides the account default). Only Hot and Cool can be set as the default account-level tier. Cold and Archive tiers can only be set at the individual blob level.
</Callout>

### Lifecycle Management

<KeyTerm term="Lifecycle Management">A feature that lets you define rule-based policies to automatically transition blobs between access tiers or delete them based on age or other conditions. For example, you can create a rule that moves blobs to the Cool tier 30 days after creation and to Archive after 180 days.</KeyTerm>

Rather than manually moving blobs between tiers, lifecycle management policies automate the process. You define rules like:

- Move blobs to Cool 30 days after last modification
- Move blobs to Archive 180 days after last modification
- Delete blobs 365 days after creation

This ensures data is always stored at the optimal cost tier without manual intervention.

<DeepDive title="Access Tiers and Cost Optimization in Practice">
Consider a media company that stores video files in Azure Blob Storage:

1. **Day 0-30 (Hot tier):** A new video is uploaded and frequently accessed by editors and viewers. The Hot tier's low access costs keep read operations cheap despite many downloads.

2. **Day 31-90 (Cool tier):** After a month, the video gets less traffic. A lifecycle policy automatically moves it to Cool, cutting storage costs while accepting slightly higher per-access charges for the reduced number of views.

3. **Day 91-180 (Cold tier):** After three months, the video is rarely viewed. It moves to Cold tier for even lower storage costs. The occasional view costs more per access, but the total cost is far lower because views are so rare.

4. **Day 181+ (Archive tier):** After six months, the video is moved to Archive for long-term retention at minimal storage cost. If a viewer requests it, the company rehydrates the blob to the Hot tier (taking up to 15 hours) before serving it.

This tiered approach can reduce storage costs by 60-80% compared to keeping all data in the Hot tier.
</DeepDive>

## Data Migration Tools

Azure provides several tools for migrating data to the cloud, each designed for different scenarios and data volumes.

### Azure Migrate

<KeyTerm term="Azure Migrate">A centralized hub for discovering, assessing, and migrating on-premises workloads to Azure. It provides tools for assessing servers, databases, web apps, and virtual desktops, generating right-sizing recommendations and cost estimates, and orchestrating the migration itself.</KeyTerm>

Azure Migrate is not just a data migration tool — it is a complete migration platform. It helps you:

- **Discover** what you have on-premises (servers, databases, dependencies)
- **Assess** readiness and compatibility with Azure services
- **Estimate** costs for running workloads in Azure
- **Migrate** servers, databases, and applications with minimal downtime

### Azure Data Box

<KeyTerm term="Azure Data Box">A physical device provided by Microsoft for transferring large amounts of data to Azure offline. Microsoft ships a rugged, tamper-resistant storage device to your location. You copy your data onto it and ship it back to Microsoft, who uploads the data to your Azure storage account.</KeyTerm>

When you have terabytes or petabytes of data to move to Azure, transferring it over the network could take weeks or months — even with a fast connection. Azure Data Box solves this with a physical device. Microsoft ships you a storage appliance (Data Box holds up to 80 TB, Data Box Heavy holds up to 1 PB), you copy your data to it, and ship it back. Microsoft then uploads your data to your storage account.

Data Box is ideal when:
- Network transfer would take too long (weeks or months)
- Bandwidth is limited or expensive
- You need to move a one-time, large volume of data to Azure

### AzCopy

**AzCopy** is a command-line utility for copying data to and from Azure Storage accounts. It supports copying data between storage accounts, uploading files from your local machine to Azure, and downloading data from Azure. AzCopy is optimized for performance with multi-threaded transfers and supports resumable transfers for large files.

### Azure Storage Explorer

**Azure Storage Explorer** is a free, standalone GUI application for managing Azure Storage data from your desktop. It provides a visual interface for browsing, uploading, downloading, and managing blobs, files, queues, and tables across multiple storage accounts and subscriptions. Think of it as a graphical file manager for Azure Storage.

<Callout type="info">
For the AZ-900 exam, remember these migration tool pairings: **Azure Migrate** is for discovering, assessing, and migrating workloads (servers, databases, apps). **Azure Data Box** is for large-scale offline data transfer using a physical device. **AzCopy** is a command-line tool for copying storage data. **Storage Explorer** is a GUI tool for browsing and managing storage.
</Callout>

<KeyTakeaways>
- **Azure Storage Account** is a unique namespace that groups Blob, Files, Queue, and Table services. Account names must be 3-24 characters, lowercase letters and numbers only, and globally unique.
- **Storage redundancy** ranges from LRS (3 copies, 1 data center) to RA-GZRS (6 copies across 2 regions with secondary read access). More redundancy means higher durability and cost.
- **Blob Storage** stores unstructured data (images, videos, backups) in containers. Three blob types: **block** (general files), **append** (logs), **page** (VM disks).
- **Azure Files** provides managed SMB/NFS file shares that can be mounted as network drives — ideal for lift-and-shift migrations.
- **Queue Storage** enables asynchronous messaging between application components for decoupling and load leveling.
- **Table Storage** is a NoSQL key-value store for structured, non-relational data using partition keys and row keys.
- **Access tiers** optimize cost: Hot (frequent access), Cool (30-day min, lower storage cost), Cold (90-day min), Archive (180-day min, offline, requires rehydration). Lifecycle management policies automate tier transitions.
- **Migration tools**: Azure Migrate (discover, assess, migrate workloads), Azure Data Box (physical device for large offline transfers), AzCopy (CLI data copy tool), Storage Explorer (GUI management tool).
</KeyTakeaways>
